# CSS inlay hint 管线设计

目标: 从已经验证可用的映射表 MVP 出发，把 CSS inlay hint 设计成一条更稳定、更可演进的管线。

核心方向:
- 不再依赖手工维护散落数组作为最终真相。
- 让规范数据、分类规则、输出策略分层。
- 让实现更接近 clangd 的调度链: 入口薄、语义集中、输出统一。
- 以后标准变化时，优先更新数据源或生成产物，而不是直接改遍历逻辑。

## 1. 当前状态

我们已经证明了一件事:
- 基于映射表的第一版 MVP 可以在 VS Code 里正常显示。
- 这个 MVP 证明了左侧 hint、范围过滤、候选收集、最终渲染这条链路是可行的。

当前实现的价值:
- 已经能验证视觉效果和用户感知。
- 已经能验证 box-first 的保守策略。
- 已经能验证 hint 侧边、label、padding、范围限制这些输出细节。

当前实现的局限:
- 映射表更像设计稿，不适合作为长期唯一真相来源。
- 规则分类仍然偏手工。
- 如果以后规范变化，靠人工维护数组会越来越脆弱。

因此下一步不是继续堆规则，而是把规则放进一条规范化管线。

## 2. clangd 调度链给我们的启发

我们学习 clangd 的重点，不是抄实现，而是抄分层方式。

### 2.1 入口层只负责注册和转发

clangd 的 LSP server 会先把 method 绑定好，再把标准请求转发给服务层。

启发:
- CSS hinter 也应该有一层薄入口。
- 这层只负责接收 `textDocument/inlayHint`，不负责规则判断。
- 入口层的职责是把 LSP 参数转换成内部请求上下文。

### 2.2 服务层只负责调度和准备上下文

clangd 的服务层会先保证 AST 可用，再进入真正的 hint 生成逻辑。

启发:
- CSS hinter 也应该有一层调度层。
- 它负责拿文档快照、解析 AST、准备配置、准备范围。
- 它不做具体分类，不拼接最终文本。

### 2.3 核心层只负责语义生成

clangd 的顶层 inlay hint 函数会构造 visitor，遍历 AST，最后统一去重和排序。

启发:
- CSS hinter 也应该把“候选收集”和“最终输出”分开。
- 语义层负责产出候选。
- 输出层负责统一渲染、过滤、去重、排序和稳定落点。

### 2.4 visitor 是状态打包器，不是杂糅逻辑的地方

clangd 的 visitor 构造函数会把 AST、token buffer、打印策略、主文件缓存等一次性装进去。

启发:
- CSS hinter 的语义执行器也应该持有必要上下文。
- 但它不应该在遍历过程中临时拼接大量逻辑。
- 上下文打包后，规则可以保持小而稳定。

## 3. 我们的目标架构

建议把 CSS inlay hint 拆成六层。

### 3.1 输入层

职责:
- 接收文档、请求范围、配置和编辑器上下文。

输出:
- 一个标准化的内部请求对象。

原则:
- 只做协议转换，不做语义判断。

### 3.2 解析层

职责:
- 把文档解析成 CSS AST / PSI。
- 保留节点、范围、子节点关系。

输出:
- 可遍历的语义树。

原则:
- 不解析字符串正则。
- 尽量利用现成 parser 的 node 类型。

### 3.3 语义层

职责:
- 识别 declaration、value、property family、token 形态、引用关系。
- 把 AST 上的节点归一成可比较的语义候选。

输出:
- 候选项列表。

原则:
- 语义层只描述“是什么”，不决定“怎么显示”。
- 同一类规则尽量统一分类器，不要分散到各个输出分支。

### 3.4 判定层

职责:
- 决定候选是否值得提示。
- 处理 suppress、defer、合并、降噪。

输出:
- 经过筛选的候选项。

原则:
- 能从源码直接看出来的信息，尽量不重复提示。
- 低价值场景默认压制。
- 有歧义的 case 默认延后，不硬做。

### 3.5 落点层

职责:
- 决定 hint 挂在左侧、右侧、行尾还是块尾。
- 计算范围是否稳定、是否可见、是否在请求范围内。

输出:
- 带最终位置的候选项。

原则:
- 位置稳定优先于完整覆盖。
- 落点不稳就不要显示。

### 3.6 输出层

职责:
- 统一构造 InlayHint。
- 统一做排序、去重、长度控制、样式统一。

输出:
- 最终展示给编辑器的 hint 列表。

原则:
- 输出层不反推复杂语义。
- 输出层只消费已经判定好的结果。

## 4. 数据来源与分层

我们不应该把手工数组当最终真相，而应该把它当中间层。

### 4.1 Source data

这层应该尽量来自规范或标准化数据源。

候选来源:
- `mdn-data`
- `css-shorthand-properties`
- 未来可加入的浏览器支持数据、标准版本数据、兼容性元数据

职责:
- 表达规范事实。
- 表达属性分组、缩写家族、语法特征、值类型。

### 4.2 Generated registry

这层是从 source data 生成出来的本地产物。

职责:
- 把规范事实转成可快速查询的 registry。
- 为运行时提供稳定的 family / rule / classifier 结构。

特点:
- 可重建。
- 可版本化。
- 可在测试里固定。

### 4.3 Runtime overrides

这层保留少量手写策略。

适合内容:
- MVP 阶段的保守白名单。
- 语义太歧义的 suppress 规则。
- 个别需要人工兜底的例外。

原则:
- 手写规则只做策略，不做主数据。

## 5. 候选项模型

建议把每个候选统一成一个中间对象。

建议字段:
- propertyName
- family
- valueNode
- tokenShape
- semanticKind
- side
- label
- priority
- range
- reason

为什么要这么做:
- 以后不管是 box、flex、grid 还是别的 CSS 语义，都能走同一条管线。
- 这样输出层不需要知道每个 family 的内部细节。

## 6. 第二阶段要补的关键规则

第二阶段不应该再靠“数组直接写例子”，而应该靠 AST 分类。

### 6.1 flex

需要识别的语义形态:
- `none` -> suppress
- global values -> 未来右侧 hint
- `1` -> 单值 grow
- `auto` / `10em` / `30%` / `min-content` -> 单值 basis
- `1 30px` -> grow + basis
- `2 2` -> grow + shrink
- `2 2 10%` -> grow + shrink + basis

关键点:
- 两值情况不能只看 arity。
- 第二个 token 需要 token class / AST 类型辅助判断。

### 6.2 flex-flow

需要识别的语义形态:
- 单个 direction keyword
- 单个 wrap keyword
- direction + wrap
- global values -> 未来右侧 hint

关键点:
- 一个 token 可能是方向，也可能是换行，因此要做 keyword classifier。

### 6.3 grid 系列

先保守看待:
- `grid-area`
- `grid-row`
- `grid-column`

原则:
- 先做稳定的、可分段的形式。
- `grid` / `grid-template` 暂时延后。

## 7. 左右侧与未来右侧

当前原则:
- 第二批核心规则先以左侧 hint 为主。
- `none` 类语义先 suppress。
- `global values` 保留为未来右侧 hint。

原因:
- 左侧更适合角色标签。
- 右侧更适合结果摘要。
- 现在先把结构型提示做稳，再考虑结果型提示。

## 8. 更新策略

为了避免以后人工改数组失控，建议采用下面的更新顺序。

### 8.1 先改 source data

标准变化时，先更新规范数据或生成它的脚本。

### 8.2 再重生成 registry

把新数据导出成可查询的 family/rule registry。

### 8.3 最后只微调 runtime overrides

只有少量保守性判断需要手写。

这样就能做到:
- 标准变化 -> 数据更新
- 行为变化 -> registry 重建
- 特殊策略 -> 少量 override

## 9. 实现路线

建议按这几个阶段推进:

1. 保持当前 MVP 继续可用。
2. 建立 AST 分类器，替代正则式猜测。
3. 把 `flex` / `flex-flow` 的语义收敛成统一候选模型。
4. 引入 generated registry，减少手工数组。
5. 把输出层和落点层独立出来，统一去重和排序。
6. 再扩展到 `grid` 系列和更后面的 layout 家族。

## 10. 设计结论

结论很明确:
- 要做 clangd 风格的分层管线。
- 不能长期依赖手工数组作为唯一实现。
- 应该让规范数据驱动分类，让 runtime 只做薄调度和薄渲染。
- 当前的映射表 MVP 证明了方向可行，但它只是过渡层，不是终局。

下一步最值得做的事:
- 把 `flex` / `flex-flow` 的规则从“文本映射”转成“AST 分类 + 语义候选”。
- 同时补一份更明确的 generated registry 设计，作为后续实现的桥梁。
