基于你提供的 `重写关键调度链.md` 深度分析，特别是参考 `clangd` 中 `processCall`（语义加工）、`addBlockEndHint`（块尾专用出口）和 `computeBlockEndHintRange`（落点判定器）的分离设计，我们需要对原有的 **规则引擎层** 和 **输出渲染层** 进行重构。

核心变化点：
1.  **规则引擎层拆分**：将“匹配分类”与“语义映射/过滤”显式分离，模仿 `VisitCallExpr` (归一化) -> `processCall` (决策) 的流程。
2.  **输出渲染层升级**：不再只是简单的“挂后面”，而是引入 **Placement Strategy（落点策略）** 模式。区分 **行内参数式 (Inline Parameter)** 和 **块尾注释式 (Block End)**，并引入独立的 **落点判定器 (Placement Resolver)**，模仿 `computeBlockEndHintRange` 的逻辑，确保块级提示的稳定性。

以下是重新设计的详细架构：

---

### 4. 规则引擎层 (Rule Engine) —— **语义决策中心**
*   **clangd 参考：** `VisitCallExpr` (归一化), `processCall` (核心决策), `shouldHintName`, `isSetter` (过滤 heuristic)
*   **设计理念：** 这一层**只决定“显示什么内容”和“属于哪种语义类型”**，绝不触碰具体的坐标计算。它将原始候选转化为带有**语义标签 (Semantic Label)** 和 **提示策略 (Hint Strategy)** 的中间对象。
*   **内部子分层：**
    1.  **Classifier (分类器)**: 识别语法模式 (如 `margin-2-values`, `flex-grow-basis`)。
    2.  **Mapper & Filter (映射与过滤器)**: 应用业务规则，生成文本，决定抑制。
    3.  **Strategy Annotator (策略标注器)**: 标记该 Hint 是 `Inline` (行内) 还是 `BlockEnd` (块尾)。

#### 详细职责与流程
*   **输入**: `CssHintCandidate` (来自采集层，包含 property, tokens, ranges)。
*   **处理逻辑**:
    1.  **模式匹配 (Pattern Matching)**:
        *   加载 JSON 规则，匹配 Token 流类型。
        *   *Example:* `margin: 10px 20px` -> 匹配 `Form: 2-values`。
    2.  **语义映射 (Semantic Mapping)**:
        *   根据匹配结果生成 Labels。
        *   *Example:* `['top/bottom', 'left/right']`。
        *   处理顺序互换 (如 `flex-flow`)，调整 Label 顺序以匹配物理 Token。
    3.  **启发式过滤 (Heuristic Filtering)** (参考 `shouldHintName`, `isSetter`):
        *   **全局值抑制**: `inherit`, `initial`, `unset` -> **Suppress**。
        *   **显式覆盖检测**: 如果用户已经写了 `margin-top: ...`，则简写提示可能被抑制 (取决于配置)。
        *   **变量解析失败**: `var(--unknown)` -> **Suppress** (保守策略)。
        *   **低价值场景**: 值与默认值完全一致且配置要求隐藏时 -> **Suppress**。
    4.  **策略标注 (Strategy Annotation)**:
        *   为每个生成的 Hint 打上 `HintKind` 标签：
            *   `Parameter`: 行内参数名 (如 `/* top */`)。
            *   `Type`: 类型或单位提示。
            *   `BlockEnd`: **关键新增**。用于规则块结束后的总结性提示 (如 `/* .container */` 在 `}` 后)。

*   **输出**: `SemanticHintInstruction` 列表。
    ```typescript
    interface SemanticHintInstruction {
      label: string;                // "top/bottom"
      kind: InlayHintKind;          // Parameter | BlockEnd
      strategy: 'inline-right' | 'block-end-right'; // 决定去哪一层渲染
      sourceTokenIndex?: number;    // 关联到哪个 Token (inline 用)
      associatedBlockRange?: Range; // 关联到哪个代码块 (block-end 用)
      tooltip?: string;             // 悬停文档
      suppressReason?: string;      // 如果被过滤，记录原因 (用于调试)
    }
    ```

---

### 5. 输出渲染层 (Output Renderer) —— **落点稳定器**
*   **clangd 参考：** `addInlayHint` (统一入口), `addBlockEndHint` (块尾专用), `computeBlockEndHintRange` (落点判定), `dedupeAndSort`
*   **设计理念：** 这一层**只关心“挂在哪里”和“怎么画”**。它接收带策略的指令，调用专门的 **Placement Resolver** 计算精确范围，确保提示“看得见、挂得稳、不遮挡”。
*   **关键升级：** 引入 **Block-Aware Placement**，不仅处理行内值，还能处理 CSS 规则块 (`{ ... }`) 的结尾。

#### 详细职责与流程
*   **输入**: `SemanticHintInstruction[]` + `TextDocument` (快照)。
*   **处理逻辑**:
    1.  **路由分发 (Routing)**:
        *   根据 `strategy` 将指令分发给不同的 **Placement Resolver**。
    2.  **落点判定 (Placement Resolution)** (核心难点):
        *   **Case A: Inline Parameter (行内)** (参考 `getHintRange`)
            *   定位：找到 `sourceTokenIndex` 对应 Token 的 `end` 位置。
            *   稳定性检查：确保不在字符串中间，不与其他 Hint 重叠。
            *   侧边决策：通常挂在右侧 (`paddingLeft: true`)。
        *   **Case B: Block End (块尾)** (参考 `computeBlockEndHintRange`)
            *   **目标**: 在 CSS 规则块结束的 `}` 之后显示提示 (例如显示选择器名称或嵌套层级)。
            *   **判定逻辑 (严格)**:
                1.  **主文件检查**: 开始和结束括号必须在当前编辑的主文件中。
                2.  **行尾检查**: `}` 必须是该行最后一个非空白字符 (或仅允许跟随 `;` 或 `!important`)。
                3.  **最小行数限制**: 块的高度必须超过 N 行 (如 3 行)，避免单行规则 `{ color: red; }` 也显示块尾提示造成噪音。
                4.  **精确落点**: 计算 `}` 之后的具体 Range，确保 Hint 紧贴 `}` 但不覆盖它。
            *   **失败处理**: 如果上述任一条件不满足，**直接丢弃该 Hint** (宁缺毋滥)。
    3.  **格式化与构造 (Formatting & Construction)**:
        *   根据 `kind` 添加前缀/后缀 (如 BlockEnd 自动加 `/* ... */` 样式)。
        *   长度裁剪：如果 Label 过长，截断或丢弃。
    4.  **全局治理 (Global Governance)**:
        *   **去重 (Deduplication)**: 同一位置不要显示多个相同内容的 Hint。
        *   **排序 (Sorting)**: 按 Position 顺序排序，符合 LSP 协议要求。
        *   **可见性裁剪**: 移除超出 LSP 请求 `range` 的 Hint。

*   **输出**: `InlayHint[]` (标准 LSP 协议对象)。
    ```typescript
    // 最终返回给 VS Code / Neovim 的对象
    [
      {
        position: { line: 10, character: 25 }, // 精确计算后的位置
        label: "/* top/bottom */",
        kind: 2, // Parameter
        paddingLeft: true,
        paddingRight: false,
        tooltip: "Sets the margin area on the top and bottom."
      },
      {
        position: { line: 15, character: 1 }, // } 之后的位置
        label: "/* .container */",
        kind: 3, // BlockEnd (custom mapping)
        paddingLeft: true,
        paddingRight: false,
        tooltip: "End of .container rule"
      }
    ]
    ```

### 💡 核心改进点对比

| 特性 | 原设计 | **新设计 (基于 clangd 参考)** | 优势 |
| :--- | :--- | :--- | :--- |
| **规则逻辑** | 混合匹配与过滤 | **Classifier + Mapper/Filter 分离** | 逻辑更清晰，易于单元测试；方便扩展新的过滤 heuristic。 |
| **块级支持** | 未明确提及 | **显式支持 `BlockEnd` 策略** | 能处理 CSS 嵌套块、媒体查询块的结尾提示，提升长文件可读性。 |
| **落点计算** | 简单挂在 Token 后 | **引入 `Placement Resolver` 模式** | 借鉴 `computeBlockEndHintRange`，严格校验行尾、主文件、块大小，**杜绝乱码和错位**。 |
| **稳定性** | 依赖基础逻辑 | **保守策略 (Fail-Fast)** | 块尾提示若条件不满足直接丢弃，保证“显示的必是稳定的”，符合 clangd 哲学。 |
| **扩展性** | 需改代码 | **配置驱动 + 策略模式** | 新增属性只需改 JSON；新增提示类型 (如 Type Hint) 只需加一个新 Strategy。 |


这个设计完全吸收了你提供的 `clangd` 源码分析精华，既保证了行内提示的灵活性，又通过严格的判定器解决了块级提示的稳定性难题。
