**绝对不需要手工检验！** 如果靠人眼去检查成千上万个生成的测试用例是否合法，那测试本身就失去了意义。

在编译器/语言服务器开发中，我们利用 **“规范即代码（Schema as Code）”** 和 **“解析器即预言机（Parser as Oracle）”** 来实现全自动验证。

既然你熟悉深度学习，可以把这理解为：你不需要人工标注每一个样本是“正例”还是“负例”，而是有一个**预训练好的判别模型（CSS Parser）** 自动给你打标签。

以下是三种自动化验证策略，按推荐程度排序：

---

### 策略一：解析器自证（Parser as Oracle）—— 最推荐 ✅

这是最核心的方法。你的 LSP 依赖 `vscode-css-languageservice` 来解析 CSS。
*   **逻辑：** 如果生成器基于正确的规则生成了代码，那么**解析器必须能成功解析它且不报错**。
*   **流程：**
    1.  **生成：** 组合生成 `margin: 10px auto;`。
    2.  **验证：** 调用 `cssLanguageService.parseStylesheet(textDocument)`。
    3.  **断言：**
        *   检查返回的 AST 中是否有 `error` 节点。
        *   检查 `diagnostics` 列表是否为空（或者只包含预期的警告）。
    4.  **结论：** 如果解析报错，说明**生成器的规则定义错了**（比如允许了 `margin` 接受 `solid` 这种非法值），而不是用例本身的问题。

**代码示例 (Vitest/Jest)：**

```typescript
import { getCSSLanguageService } from 'vscode-css-languageservice';
import { generateCases } from './generator'; // 你的生成器

const cssLS = getCSSLanguageService();

test('Auto-generated cases must be syntactically valid', () => {
  const cases = generateCases('margin'); // 生成 500 个用例

  cases.forEach(({ code, description }) => {
    const document = TextDocument.create('test://test.css', 'css', 1, code);
    const stylesheet = cssLS.parseStylesheet(document);
    const diagnostics = cssLS.doValidation(document, stylesheet);

    // 核心断言：生成的代码必须能被官方解析器完美解析
    expect(diagnostics).toHaveLength(0); 
    
    // 可选：确保 AST 里没有 error 节点
    // visitNode(stylesheet, node => { expect(node.type).not.toBe('error') });
  });
});
```

**优点：** 只要你的生成逻辑是基于元数据（Schema）的，且解析器是正确的，那么生成的用例**天然合法**。如果测试失败，直接修复生成器的配置 JSON 即可。

---

### 策略二：基于 Schema 的构造性生成（Constructive Generation）

不要随机采样，而是**基于语法树生成**。
*   **原理：** 就像大语言模型（LLM）基于概率生成 token 一样，你的生成器应该基于 CSS 语法定义（Grammar）递归构建字符串。
*   **逻辑：**
    *   `margin` 的规则是 `<margin-width>{1,4}`。
    *   `<margin-width>` 的定义是 `<length> | <percentage> | auto | ...`。
    *   生成器直接从 `<length>` 的定义池子里取一个值（如 `10px`）。
*   **结论：** 既然是严格按照语法定义拼出来的，**它一定是合法的**。这就像数学证明，不需要验证结果，因为过程保证了结果的正确性。

**如何实现：**
利用 `mdn-data` 或 `vscode-css-languageservice` 中的 `syntax` 字段（例如 `<'flex-grow'> <'flex-shrink'>? || <'flex-basis'>`），编写一个简单的递归下降生成器。

---

### 策略三：黄金主文件比对（Golden Master Testing）

对于复杂的语义（比如 Hint 显示的位置和内容），我们不仅关心“代码是否合法”，还关心"Hint 对不对”。

*   **流程：**
    1.  **生成合法用例：** 使用策略一确保代码合法。
    2.  **运行 LSP：** 将代码发给你的 LSP Server。
    3.  **捕获输出：** 记录 LSP 返回的 Inlay Hints。
    4.  **人工审核一次（仅一次）：** 第一次运行时，你人工检查生成的 `snapshot` 文件（包含代码 + 期望的 Hint）。
    5.  **固化快照：** 将结果保存为 `.snap` 文件。
    6.  **回归测试：** 以后每次代码修改，自动比对当前输出和 `.snap` 文件。如果有差异，测试失败。

**优点：** 只需要人工审核一次。之后任何逻辑变更导致的 Hint 变化都会被自动捕捉。

---

### 针对你提到的“采样定理”的修正

回到你之前的想法，这里不需要拉丁超立方采样（LHS），因为：
1.  **空间是离散的：** CSS 属性值是枚举或特定格式，不是连续浮点数。
2.  **约束是硬性的：** `border-style: 10px` 是 100% 非法的，不存在“接近合法”的状态。LHS 可能会生成这种垃圾数据浪费算力。
3.  **目标是覆盖分支：** 我们需要覆盖的是语法树的每一条路径（Path Coverage），而不是分布的均匀性。

**正确的“采样”策略是：组合测试（Combinatorial Testing）**
使用 `all-pairs` 或 `fast-cartesian` 库，确保：
*   每个属性的 **1 值、2 值、3 值、4 值** 情况都被测到。
*   每种值类型（Length, %, Auto, Calc, Var）在所有位置都至少出现一次。
*   每两种类型的组合（如 `Length + %`）至少出现一次。

这样生成的用例数量通常在几百个左右，既能保证**100% 的逻辑覆盖**，又能通过**解析器自证**确保全部合法。

### 总结工作流

1.  **定义规则 (JSON)：** 描述 `margin` 允许哪些 Token 类型。
2.  **生成用例 (Script)：** 根据规则笛卡尔积生成代码字符串。
3.  **自动验证 (Test Suite)：**
    *   Step A: 调用 `vscode-css-languageservice` 解析。**失败 -> 规则定义错误。**
    *   Step B: 调用你的 LSP 获取 Hint。
    *   Step C: 比对 Snapshot。**失败 -> 逻辑回归错误。**

**完全不需要人工逐个检查合法性。** 只有当解析器都报错了，你才需要介入，而那通常意味着你的规则配置文件写错了（比如把 `solid` 放进了 `margin` 的允许列表），修好配置重新生成即可。

### 7. 关于“剪枝”的最终原则

这里的“剪枝”只能由代码完成，不能由人手工完成。

*   **禁止人工剪枝：** 不允许人工浏览生成结果后再挑合法样本，这会把测试退化成半自动标注。
*   **允许规则剪枝：** 剪枝必须写进生成器本身，由 Schema、语法约束、属性元数据和解析器反馈共同决定。
*   **允许自动回收：** 如果某批生成结果被解析器判定为非法，先修正规则定义，再重新生成，不保留人工修补痕迹。
*   **允许自动分层：** 生成器可以自动分出合法样本、预期抑制样本、边界样本，但分层规则必须是代码，不是人眼判断。

最终目标不是“人工筛出一批看起来对的用例”，而是“把规则写对，让生成器只产出对的用例”。
